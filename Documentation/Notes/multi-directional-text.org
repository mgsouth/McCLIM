
* Text directions in scripts around the world

Generally embedding horizontal text inside a vertical one requires us to rotate
it by pi/2 CW. W3C adds CSS properties that allow customization for that.

Glossary:

- sinistrodextrally :: left to right, LTR
- dextrosinistrally :: right to left, RTL
- boustrophedonically :: alternating line direction, oxturn + mirrored

- oxturn :: alternating line direction, OXT (horizontal or vertical)

  I'll refer to all custom alternating directions as oxturn-foo, where foo
  denotes the initial side (i.e oxturn-left, oxturn-top).

* Script Examples

Mind that I don't know what the following texts state. Some languages have
examples while other doesn't have them (we substitute with Latin text instead).

When I say "left-to-right / top-to-bottom" I mean first the line direction, and
then the page direction. Some languages have no examples, and some directions
are listed without even example language.

In short, we have all possible directions for both lines and pages, including
oxturn. I have not found some particular combinations, most notably
"bottom-to-top / right-to-left" and "right-to-left / bottom-to-top". Also oxturn
combinations are few, but there are both vertical and horizontal variants.

** Horizontal Scripts

- left-to-right / top-to-bottom :: Latin, Eastern Asian

  1. English :: "The quick brown fox jumps over the lazy dog."
  2. Japanese :: "あなたは美しいです。あなたは素晴らしいです。"

- right-to-left / top-to-bottom :: Arabic, Hebrew

  1. Arabic :: "نشاط التدويل"
  2. Hebrew :: "הנה כמה מילות"

- left-to-right / bottom-to-top :: Hanunó'o
- right-to-left / bottom-to-top :: ???
- oxturn-left   / bottom-to-top :: ancient egyptian paintings
- boustrophedon / top-to-bottom :: ancient Greece (stone tablets), Etruscan, ...

  Line directions are alternating just like you plow the field with an ox. After
  changing the direction, the text itself is mirrored.

- reverse-boustrophedon / top-to-bottom :: Rapa Nui (historical)

  Like boustrophedon, but instead of mirroring, alternating lines were rotated
  by pi (180 degrees).

** Vertical Scripts

- top-to-bottom / right-to-left :: traditional Eastern Asian
  
  1. Japanese "あなたは美しいです。あなたは素晴らしいです。"
  2. Chinese "国际化活动"

- top-to-bottom / left-to-right :: traditional Mongolian (and ancestors)

  1. Mongolian "ᠬᠢᠳᠠᠳ ᠮᠣᠩᠭᠤᠯ ᠲᠣᠯᠢ ᠭᠠᠷᠭᠠᠵᠠᠢ ᠁"

- bottom-to-top / left-to-right :: Ogham (Old Irish) -- both orientations

  1. Ogham "ᚋᚉᚉᚂᚔᚋ" :: rotate glyphs horizontally by pi/2 CCW

- bottom-to-top / right-to-left :: ???
- oxturn-bottom / right-to-left :: Mixtec (Tiger's Claw)

* McCLIM specification

McCLIM page formatting supports now four major directions of line and page:
left-to-right, right-to-left, top-to-bottom and bottom-to-top. The stream is
responsible for stitching individual output records that may have its own
orientation (i.e bidi text has "chunks" of different directionality).

From the perspective of the operator ~{medium-}draw-text~ we have a combination
of many arguments that add up to the text direction:

- toward-point - specifies the baseline
- align-x/align-y - specifies text alignment relative to the (ltr) baseline
- transform-glyphs - specifies whether the text size should be transformed

Note that the alignment arguments are relative to the baseline treated as a
horizontal line going from left to right, disregarding of the actual line
direction. For example when the baseline is oriented vertically in screen
coordinates, then ~:align-y :top~ will move the rectangle with text the left.

Normally the text size does not depend on the medium transformation. It is
similar to the line-style-unit :normal, where the line thickness is ignores the
medium transformation. When ~transform-glyphs~ is true, then the text is
transformed similar to the line when line-style-unit is ~:coordinate~.

** Bounding rectangle

Depending on the backend it may not be possible to change the baseline
(console), or to transform the text (console, x11 w/o xrender). McCLIM core
requires the information about the bounding rectangle of graphics to decide hit
tests, highlight records and format output. This is why core needs to ask the
backend about the bounding rectangle for text on a specified baseline.
